How to use this (30-sec read)

Purpose: not to re-learn — to reload which tools exist and the trigger signal for each, so when a problem hits, your brain jumps to candidates fast. Skim the "Signal → Tool" table first; dip into a section only if a tool feels rusty.
For this style of test (function signature, examples-heavy, weird return like an index not a value): (1) trace every example by hand first — the examples ARE the spec; (2) confirm exactly what to return (value? index? count? format?) before coding; (3) write your own edge-case tests. Signal-spotting matters more than raw difficulty.

Sliding Window

int l=0; for(int r=0;r<n;r++){
  add(a[r]);
  while(invalid) remove(a[l++]);
  best = update(r-l+1);
}
Fixed-size: slide by 1. Variable: shrink while condition breaks. Track state in a map/count.

Binary Search

int lo=0, hi=n-1;
while(lo<=hi){
  int m=lo+(hi-lo)/2;
  if(ok(m)) hi=m-1; else lo=m+1;
}
return lo; // first index where ok() true
"Binary search on the answer": if you can check "is X feasible?" monotonically, binary-search X. (minimize-the-max problems)

Backtracking

void bt(path, choices){
  if(done){ save(path); return; }
  for(c : choices){
    path.add(c);
    bt(path, next(choices,c));
    path.remove(last);   // undo
  }
}
subsets / permutations / combinations / N-queens / word search. Prune early when possible.

✅ Per-question checklist (每題開始前 30 秒)

StepDo
1Trace every example by hand — reverse-engineer the rule (esp. weird returns like index/count/format)
2Confirm the return: value? index? count? boolean? what format?
3Match a signal → tool from the master table
4Note constraints: n size → target complexity (n≤10⁴ ok O(n²); n≥10⁵ needs O(n log n))
5Code the simplest correct version — AC first, optimize only if needed
6Test edge cases: empty, single element, all same, negatives, boundaries — write your own tests
Mindset: vague/animation-only problems favor you — you've done 470+ contests. Stay calm, let the examples be the spec, and let the signal table jump the tool to your hand.
