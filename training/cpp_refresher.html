Modern C++ — the "you missed these" essentials

auto — type inference

auto x = 42;              // int
auto it = vec.begin();   // no more std::vector<int>::iterator
auto& ref = obj;         // auto with reference (keep the &!)
const auto& r = getBig();// read-only, no copy

auto drops references & const by default → use auto&, const auto& when you want them. Forgetting the & silently makes a copy — a classic perf bug.

Range-for

for (const auto& item : container) { use(item); }  // read-only, no copy
for (auto& item : container) { item.mutate(); }    // modify in place
for (auto item : container) { }                     // COPY each — usually wrong

Lambdas

auto add = [](int a, int b) { return a + b; };
int total = 0;
std::for_each(v.begin(), v.end(), [&total](int x){ total += x; }); // [&] capture by ref
auto byVal = [=](){ return captured; };  // [=] capture by value
// capture list: [&]=all by ref, [=]=all by value, [x]=x by value, [&x]=x by ref

Capturing by reference [&] and letting the lambda outlive the referenced variable = dangling reference (use-after-free). You know this bug class from your kernel days — same trap, new syntax.

  if (found) return value;
  return std::nullopt;

Pass std::string_view for read-only string params — avoids copying. But it doesn't own the data, so don't store it beyond the source's lifetime.

Memory & RAII — the biggest shift from your era

In your CyberLink days you wrote new/delete manually. Modern C++ almost never does. This is the #1 thing an interviewer will check.

The rule: RAII (Resource Acquisition Is Initialization)

Tie a resource's lifetime to an object's scope. When the object goes out of scope, its destructor frees the resource — automatically, even on exceptions. You already know destructors; smart pointers just apply RAII to heap memory.

unique_ptr — sole ownership (your default)

auto p = std::make_unique<Widget>(args);  // heap Widget, auto-freed
p->method();
// no delete needed — freed when p leaves scope
// can't copy (sole owner), but can MOVE:
auto q = std::move(p);   // p is now null, q owns it

shared_ptr — shared ownership (ref-counted)

auto s = std::make_shared<Widget>();
auto s2 = s;             // both own it; refcount = 2
// freed when the LAST shared_ptr goes away

shared_ptr cycles leak. A → B → A with shared_ptr never hits refcount 0. Break the cycle with std::weak_ptr for the back-reference. Classic interview follow-up.

UsePointer
One owner (default choice)unique_ptr
Genuinely shared ownershipshared_ptr
Break a shared_ptr cycle / observe without owningweak_ptr
Non-owning "I just look at it"raw pointer T* or reference

Say this in interview: "I reach for unique_ptr by default, shared_ptr only when ownership is genuinely shared, and I watch for reference cycles — break them with weak_ptr. I rarely write raw new/delete anymore; RAII handles it." That single sentence shows you've made the modern shift.

The Rule of 0 / 3 / 5

  • Rule of 0: if your class members are all RAII types (smart pointers, vector, string), you need NO custom destructor/copy/move — the compiler does it right. Aim for this.
  • Rule of 3 (old): if you write one of {destructor, copy ctor, copy assign}, write all three.
  • Rule of 5 (C++11): add move ctor + move assign to the list.

Move semantics — the concept that didn't exist in your era

This is the biggest genuinely-new idea. Pre-C++11, returning a big object copied it. Move semantics lets you transfer ownership of the internals instead of copying — huge for performance.

The idea

std::vector<int> makeBig();
auto v = makeBig();   // pre-C++11: copy the whole vector. C++11: MOVE it (steal the buffer). Free.

lvalue vs rvalue (the mental model)

  • lvalue = has a name, has an address (x, vec[0])
  • rvalue = temporary, about to die (makeBig(), x + y)
  • T&& = rvalue reference = "I can safely steal from this, it's dying anyway"

std::move — "I'm done with this, you can steal it"

std::string a = "hello";
std::string b = std::move(a);  // b steals a's buffer; a is now valid-but-empty
// std::move does NOT move anything — it just CASTS to rvalue ref,
// enabling the move constructor to run. Naming is misleading.

After std::move(a), a is in a "valid but unspecified" state — don't use its value, only reassign or destroy it.

When you write a class with a move ctor

class Buffer {
  char* data; size_t n;
public:
  // move constructor: steal, don't copy
  Buffer(Buffer&& o) noexcept : data(o.data), n(o.n) {
    o.data = nullptr; o.n = 0;   // leave source empty
  }
};

For interviews you mostly need to explain move semantics, not write the ctor — and prefer Rule of 0 (use vector/string/smart-ptr members so moves are auto-generated correctly).

Interview Q&A — likely C++ questions

"Difference between unique_ptr and shared_ptr?"

unique_ptr = sole ownership, no copy (move only), zero overhead. shared_ptr = shared ownership via atomic reference count, freed when last owner dies, small overhead. Default to unique_ptr; use shared only when ownership is genuinely shared. Watch cycles → weak_ptr.

"What is RAII?"

Tie resource lifetime to object scope — acquire in constructor, release in destructor. Guarantees cleanup even on exceptions. Smart pointers, std::lock_guard, file wrappers all use it. It's why modern C++ rarely needs manual delete.

"Explain move semantics / std::move."

Move transfers ownership of an object's internals instead of copying — cheap for big objects. std::move doesn't move anything; it casts to an rvalue reference so the move constructor can run. After a move, the source is valid-but-unspecified. Enables returning big objects and storing them without copies.

"lvalue vs rvalue?"

lvalue has a name/address; rvalue is a temporary about to expire. T&& binds to rvalues → "safe to steal from." This is what enables move semantics.

"virtual functions / how does polymorphism work?"

Virtual functions enable runtime dispatch via a vtable — each polymorphic object has a vptr to its class's table of function pointers. (You know this cold from low-level work — say so.) Always give a polymorphic base class a virtual destructor, or deleting through a base pointer leaks/UB.

"When is shared_ptr a problem?"

Reference cycles (A owns B owns A) never reach refcount 0 → leak. Break with weak_ptr. Also atomic refcount has overhead — don't use shared_ptr when unique suffices.

"Stack vs heap?"

Stack: automatic, fast, LIFO, scope-bound, limited size. Heap: manual (or smart-ptr) lifetime, larger, slower to allocate, fragmentation risk. Prefer stack/RAII; heap via make_unique/make_shared.

"const correctness?"

Mark things const that don't change — params (const T&), member functions that don't mutate (void f() const), pointers. Helps the compiler and documents intent. const auto& for read-only loop/refs.
