Kubernetes — from exposure to working knowledge

You know Docker/containers, so this is the delta. K8s = orchestrator for containers at scale: it schedules containers across many machines, keeps them running, scales them, networks them. (You already met its ancestor concept — this is "Docker, but managing thousands across a cluster".)

The mental model

You give K8s a DESIRED STATE ("run 5 copies of this container").
K8s constantly makes REALITY match it (a pod dies → it starts a new one).
This is the whole idea: declarative desired-state + a control loop that reconciles.

The one sentence that shows you get K8s: "Kubernetes is a declarative control loop — you declare the desired state, and controllers continuously reconcile actual state toward it. Everything else is objects that express desired state." Say this and you sound like you understand it, not just ran commands.

Core objects (know these ~8)

ObjectWhat it is
PodSmallest unit — one (or few tightly-coupled) containers sharing network/storage. You rarely manage pods directly.
DeploymentManages a set of identical pods — desired replica count, rolling updates, rollback. Your main workhorse.
ReplicaSetKeeps N copies of a pod running (Deployment manages this for you).
ServiceStable network endpoint + load-balancing across a set of pods (pods are ephemeral, Service gives a fixed address).
IngressHTTP(S) routing from outside into Services (host/path rules, TLS). Like an L7 router.
ConfigMap / SecretConfig & secrets injected into pods (Secret = base64, needs encryption-at-rest / external KMS for real security).
NamespaceLogical partition of a cluster (team/env isolation).
StatefulSet / DaemonSet / JobStateful apps (stable identity/storage) / one-pod-per-node / run-to-completion tasks.

Architecture (control plane vs nodes)

PartRole
API serverThe front door — everything talks to it (kubectl, controllers). Stores state in etcd.
etcdThe cluster's database (key-value) — the source of truth for desired + actual state.
SchedulerDecides which node a new pod runs on (bin-packing by resource).
Controller managerRuns the reconcile loops (e.g. "5 replicas wanted, 4 exist → start 1").
kubeletAgent on each node — actually runs the containers the API server assigned.

Ties to what you read: this is exactly Borg's shape (Borgmaster ≈ control plane, Borglet ≈ kubelet). K8s is the open-source descendant of Borg. You've seen this pattern.

kubectl commands (the operational bit you've touched)

kubectl get pods / deployments / services / nodes    # list
kubectl describe pod <name>        # detail + events (debug why it won't start)
kubectl logs <pod> [-f]            # container logs
kubectl apply -f manifest.yaml     # declarative create/update (the K8s way)
kubectl rollout status/undo deployment/<name>   # rolling update / rollback
kubectl exec -it <pod> -- /bin/sh  # shell into a container
kubectl scale deployment/<name> --replicas=5
kubectl get events --sort-by=.lastTimestamp     # what's happening / failing

A minimal manifest (recognize this shape)

apiVersion: apps/v1
kind: Deployment
metadata: { name: my-svc }
spec:
  replicas: 3
  selector: { matchLabels: { app: my-svc } }
  template:
    metadata: { labels: { app: my-svc } }
    spec:
      containers:
      - name: my-svc
        image: myregistry/my-svc:1.2.3
        ports: [{ containerPort: 8080 }]
        resources:
          requests: { cpu: "500m", memory: "512Mi" }
          limits:   { cpu: "1",    memory: "1Gi" }
---
apiVersion: v1
kind: Service
metadata: { name: my-svc }
spec:
  selector: { app: my-svc }
  ports: [{ port: 80, targetPort: 8080 }]

Virtualization (the "stand out" stack)

JD's stand-out list: Firecracker, KVM, OpenStack, Nutanix AHV, RedHat OpenShift. You don't have these — but knowing what each IS (working knowledge) is enough to not be lost. Depth is nice-to-have, not required.

TechWhat it is (one line)
VM vs ContainerVM = full guest OS on a hypervisor (heavy, strong isolation). Container = shares host kernel (light, weaker isolation). Know this distinction cold.
HypervisorSoftware that runs VMs. Type-1 = on bare metal (KVM, ESXi); Type-2 = on an OS (VirtualBox).
KVMLinux's built-in hypervisor (kernel module) — turns Linux into a Type-1 hypervisor. The foundation most clouds' VMs sit on.
FirecrackerAWS's microVM — ultra-lightweight VMs (boot in ~125ms) built on KVM. Powers Lambda/Fargate. Gives VM-level isolation with near-container speed. Key idea: microVM = isolation of a VM, lightness of a container.
OpenStackOpen-source "build your own IaaS cloud" — orchestrates VMs/storage/network on your own hardware. The DIY AWS.
Nutanix AHVNutanix's hypervisor (hyperconverged infra — compute+storage in one).
OpenShiftRedHat's enterprise Kubernetes distribution — K8s + extra tooling/security/CI-CD baked in. If you know K8s, OpenShift is K8s+.

The connective idea (say this): "For a GPU cloud, the core tension is isolation vs efficiency — you want to safely multi-tenant expensive GPUs. That's why microVMs like Firecracker matter: VM-grade isolation without the VM weight. Containers/K8s handle orchestration; the virtualization layer handles safe isolation of tenants on shared hardware." That shows you grasp why these exist, even without hands-on depth.

CI/CD & IaC — your strength, sharpened

This is your home turf; just have the concepts crisp since it's the heart of the role.

CI/CD in one breath

  • CI (Continuous Integration): every commit → auto build + test → catch breakage early.
  • CD (Continuous Delivery/Deployment): passing builds auto-deploy (to staging, then prod). Delivery = ready to deploy; Deployment = actually auto-deploys.
  • Release engineering: the whole discipline of getting code from commit to production safely — versioning, artifacts, staged rollout, rollback. (This role's core.)

Concepts to have ready

ConceptCrisp take
Pipeline stagesbuild → test → package (artifact/image) → deploy → verify. Gate each stage on the previous.
Artifacts / registryBuild once, promote the same artifact through envs. Container images in a registry (ECR).
Staged rolloutCanary → % ramp → 100%, with health gates + auto-rollback. Bounds blast radius of a bad release. (You know this from your work.)
Blue-greenTwo envs; switch traffic to the new one, instant rollback by switching back.
On-prem + cloud (JD)Same pipeline deploys to both — harder because envs differ; IaC + containers make it reproducible.

IaC

  • Idea: infrastructure defined in code (declarative), version-controlled, repeatable — no ClickOps. (Your REP rebuild is the poster child: from ClickOps → CDK.)
  • Tools: Terraform (cloud-agnostic, most common), AWS CDK (you used), CloudFormation, Pulumi.
  • Why it matters here: "apply" is idempotent — converge to desired state whether run once or thrice. Same declarative-reconcile idea as K8s.

Tie it together for the interview: "IaC and Kubernetes are the same philosophy — declare desired state, let a reconcile loop converge to it. My IaC/CDK background maps directly onto how K8s thinks, which is part of why I ramp on K8s fast."

Likely questions & how to approach

"Design a CI/CD pipeline for deploying a service to both on-prem and cloud."

build → test → build one container image → push to registry → deploy via IaC to each target → health-gate + rollback. Emphasize: build-once-promote-everywhere, staged rollout, idempotent IaC apply, same image both places. This is your strength — go deep.

"How does Kubernetes work / how would you deploy on K8s?"

Declarative desired-state + reconcile loop. Deployment (replicas, rolling update) + Service (stable endpoint) + Ingress (routing). kubectl apply manifests. Be honest on depth, strong on the model.

"How do you manage secrets in a pipeline / cluster?"

Never in code/images. Inject at runtime from a secrets manager (Vault, AWS Secrets Manager, K8s Secret backed by KMS). Rotate; least privilege via IAM roles. (You did IAM key rotation + CloudFrontSigner — cite it.)

"Why isolation matters on a GPU cloud / VM vs container?"

Multi-tenant on expensive shared GPUs → need strong isolation but can't afford VM overhead → microVMs (Firecracker) = VM isolation + container speed. Containers/K8s for orchestration.

"How do you make a bad release safe?"

Staged rollout (canary → ramp), health gates, auto-rollback, blue-green for instant revert, immutable artifacts. Bounds blast radius.
